# AGENTS.md

Эти правила действуют для всего репозитория. Они задают процесс работы, маршрутизацию skills и минимальный уровень качества. Подробные инженерные правила находятся в `docs/ai_coding_rules.md`.

## Источники истины и приоритеты

1. Явный запрос пользователя и критерии приёмки.
2. Этот `AGENTS.md` и более локальные `AGENTS.md`, если они появятся ниже по дереву.
3. `docs/ai_coding_rules.md` — обязательные правила для любой генерации, правки или рефакторинга кода; перед такой работой прочитай файл полностью.
4. `DESIGN.md` или `design-system/**/MASTER.md`, если они существуют; page override имеет приоритет над master.
5. Конфигурация и код проекта: `package.json`, TypeScript, Next.js, Tailwind и существующие паттерны.
6. Инструкции выбранных skills. Skill не отменяет правила репозитория и не расширяет полномочия пользователя.

При конфликте следуй источнику с более высоким приоритетом. Не копируй значения из конфигурации в документацию: проверяй актуальное состояние проекта.

## Обязательный рабочий цикл

1. **Разведка.** Прочитай запрос, `git status --short`, затрагиваемые файлы, конфигурацию и существующие аналоги. Сохраняй пользовательские изменения и не редактируй файлы вне задачи.
2. **Маршрутизация.** Выбери минимальный набор skills по таблицам ниже. Если пользователь назвал skill — используй его. Перед применением прочитай соответствующий `SKILL.md` полностью.
3. **Контракт.** Для нетривиальной задачи зафиксируй цель, границы, критерии приёмки и самый короткий безопасный путь. Для визуальной задачи сначала зафиксируй design contract.
4. **Реализация.** Делай узкие, согласованные изменения. Предпочитай существующие зависимости, компоненты, токены и соглашения. Наличие skill само по себе не является причиной добавлять библиотеку.
5. **Проверка.** Запусти проверки, пропорциональные риску. Исправь вызванные изменением ошибки до передачи результата.
6. **Передача.** Сообщи результат, изменённые файлы, выполненные проверки и реальные ограничения. Не выдавай предположение за проверенный факт.

Работа завершена, когда выполнены критерии запроса, проверены все изменённые пути и не осталось известной ошибки, вызванной текущими изменениями.

## Маршрутизация UI/UX skills

Используй минимальный набор: один skill отвечает за направление, остальные — только за нужную специализацию.

| Skill | Вызывать когда | Не вызывать когда |
| --- | --- | --- |
| `ui-ux-pro-max` | Любая задача меняет структуру, внешний вид, responsive, accessibility, взаимодействие или воспринимаемое качество UI. Для новой страницы используй `--design-system`; для локальной проблемы — один подходящий domain; для реализации — обнаруженный stack `nextjs`. | Чистый backend, инфраструктура и невизуальные скрипты. |
| `frontend-design` | Создание новой страницы/секции или заметная смена визуального направления. Сначала определи предмет, аудиторию, единственную цель страницы и отличительную идею. | Мелкая точечная правка уже определённого стиля. |
| `design-md` | Пользователь просит создать/обновить дизайн-систему; работа охватывает несколько страниц; в проекте уже есть `DESIGN.md`. | Не создавай новый `DESIGN.md` ради одной локальной правки. |
| `build-awwwards-quality-sites` | Явно запрошен premium, cinematic, interactive, high-concept или Awwwards-level маркетинговый сайт/редизайн. | Обычный CRUD, административный интерфейс или небольшая компонентная правка. |
| `motion-design` | Любая новая анимация, переход, micro-interaction, loading/state feedback, page transition или scroll effect. Сначала определи эмоцию, narrative и motion personality. | Статическая визуальная правка без движения. |
| `gsap-core` | GSAP выбран для tween, easing, stagger, SVG/DOM motion или нужна рекомендация движка для сложной анимации. | Пользователь или существующая реализация уже выбрали Framer Motion/CSS и GSAP не даёт явного выигрыша. |
| `gsap-timeline` | Нужно синхронизировать несколько шагов, labels, nested sequences, pause/reverse/seek. | Один независимый tween. |
| `gsap-scrolltrigger` | Scroll-linked, scrub, pin, parallax или секционная scroll choreography. | Обычный viewport reveal, который проще и чище сделать текущим движком. |
| `gsap-react` | Любой GSAP-код в React/Next.js: `useGSAP`, scoped refs, SSR и cleanup. | GSAP не используется. |
| `gsap-performance` | GSAP-сцена тяжёлая, дёргается, содержит scroll/pointer loops или проходит performance review. | До появления GSAP-кода. |
| `gsap-plugins` | Нужен конкретный plugin: SplitText, Flip, MorphSVG, DrawSVG, MotionPath, Draggable, Observer, ScrollSmoother и другие. | Не загружай каталог plugins «на всякий случай». |

### Рекомендуемые комбинации

- Новая обычная страница: `ui-ux-pro-max` + `frontend-design`; добавь `design-md`, только если нужен или уже существует design system.
- Premium landing: `ui-ux-pro-max` + `frontend-design` + `build-awwwards-quality-sites` + `motion-design`; затем только реально нужные GSAP skills.
- Анимация на текущем Framer Motion: `motion-design` + `ui-ux-pro-max`; GSAP skills не нужны.
- GSAP scroll scene в Next.js: `motion-design` + `gsap-core` + `gsap-react` + `gsap-timeline` + `gsap-scrolltrigger` + `gsap-performance`; `gsap-plugins` только при конкретном plugin.
- UI bug: `diagnosing-bugs` + `ui-ux-pro-max`; добавь motion/GSAP skill только если дефект относится к анимации.
- Дизайн-система: `design-md` + `ui-ux-pro-max` + `frontend-design`.

## Инженерный стандарт

- **KISS → YAGNI → ясность → DRY.** Сначала простое решение текущей задачи; абстракция появляется только после доказанного повторения или устойчивого seam.
- **Локальность.** Меняй минимальную связную область. Сохраняй публичное поведение, если запрос не требует его изменить.
- **Одна ответственность.** Отделяй UI, данные, эффекты, анимацию, валидацию и преобразования, когда они образуют самостоятельные причины изменения.
- **Композиция.** Для React предпочитай композицию компонентов и явные props. Держи state как можно ближе к владельцу и вычисляй derived state.
- **Server-first.** В Next.js оставляй компонент серверным по умолчанию; добавляй `"use client"` только для состояния, browser API, событий или анимации.
- **Типы.** Сохраняй strict TypeScript, точные доменные типы и явные границы внешних данных. `any` требует документированной причины.
- **Данные.** Не смешивай запросы и тяжёлую трансформацию с визуальным компонентом. Валидируй ненадёжный ввод и явно обрабатывай loading, empty, success и error.
- **Зависимости.** Сначала используй то, что уже есть. Новая библиотека должна уменьшать сложность задачи, а не дублировать текущий инструмент.
- **Комментарии.** Объясняй причину, ограничение или компромисс; очевидное выражай кодом и именами.
- **Честность.** Не создавай фальшивые отзывы, партнёрства, награды, метрики и личности. Не называй сайт награждённым без проверяемого подтверждения.

## Design contract для новой страницы или крупного редизайна

До кода зафиксируй:

1. предмет, аудиторию и одно главное действие страницы;
2. визуальный тезис, связанный с миром танца, движения, сцены и человеческой энергии;
3. 4–6 семантических цветовых токенов и роли typography;
4. композицию и последовательность секций;
5. один signature moment, ради которого страницу запомнят;
6. motion personality и три duration tokens: quick, standard, slow;
7. источник каждого важного изображения/логотипа и fallback;
8. responsive, interaction и reduced-motion стратегию.

Проведи self-critique: каждое свободное визуальное решение должно быть специфично для этого проекта, а не похоже на универсальный AI-шаблон. После утверждения направления следуй ему последовательно.

## Визуальный стандарт Luzina

- Цель — дорогой, эмоциональный, минималистичный fashion/performance/creative-studio образ, а не набор эффектных компонентов.
- Hero — тезис страницы: ясное сообщение, главное действие и один сильный визуальный образ в первом viewport.
- Иерархию несут typography, масштаб, ритм, whitespace и контраст. Декор поддерживает смысл.
- Одна выразительная идея сильнее множества конкурирующих эффектов. Ориентир: 70% typography/composition, 20% motion, 10% signature effect.
- Используй реальные тексты и материалы предметной области. UI-copy пишется со стороны посетителя: активный залог, конкретные действия, стабильная терминология.
- Используй существующие CSS variables/Tailwind tokens. Raw colors и случайные размеры в компонентах допустимы только для локальной, объяснимой визуальной необходимости.
- Сохраняй согласованность между страницами, но не превращай всё в одинаковые карточки.
- Избегай generic AI aesthetics: случайных gradient blobs, декоративных bento grids, glassmorphism повсюду, бесконечных pill-бейджей, одинаковых fade-up и чрезмерно скруглённых контейнеров.
- Важные изображения имеют deliberate crop, aspect ratio, alt, loading policy и fallback. Логотипы и social proof должны быть правдивыми.
- Проектируй hover, focus, active, loading, disabled, empty и error там, где соответствующее состояние возможно.

Если существует `DESIGN.md`, он является визуальным source of truth. Обновляй его при осознанном изменении системы, а не подгоняй реализацию в обход документа.

## Motion standard

- Каждая анимация должна объяснять hierarchy, подтверждать действие, сохранять continuity, направлять внимание или выражать характер бренда.
- Выбери одну motion personality на страницу. Для Luzina по умолчанию используй premium/energetic смесь с контролируемым easing и без мультяшного bounce; конкретный brief имеет приоритет.
- У сцены есть primary action; secondary и ambient motion остаются тише. Одновременно активно не более трети элементов, общий stagger обычно не превышает 500ms.
- Entrance замедляется к финалу, exit ускоряется, on-screen transition сглажен с двух сторон. Exit короче entrance.
- Обычные hover/focus/tap делай CSS; текущие компонентные и viewport-анимации — Framer Motion. GSAP выбирай для сложных timeline, scrub, pin, SVG/plugin и управляемых cinematic sequences.
- Один движок владеет одним свойством элемента в одной сцене. Не заставляй CSS, Framer Motion и GSAP одновременно менять один transform/opacity.
- Для последовательности используй timeline, а не цепочку случайных delays. Для GSAP в React используй `useGSAP`, scoped refs/context и cleanup; регистрируй plugin один раз.
- Анимируй преимущественно transform и opacity. Избегай layout thrashing, постоянного `will-change`, неограниченных blur и ненужной работы вне viewport.
- `prefers-reduced-motion` показывает корректное конечное состояние без scrub, parallax и ambient loops; простое сокращение duration недостаточно.
- Любой listener, observer, RAF, timeline, ScrollTrigger, split text и plugin instance должен корректно уничтожаться при unmount.
- Smooth scroll добавляй только для обоснованной cinematic-задачи; выбирай ровно один engine и проверяй keyboard, anchors, touch и reduced motion.

## Accessibility, responsive и performance gates

- Семантическая разметка, логичный heading order, keyboard navigation и заметный focus обязательны.
- Контраст обычного текста не ниже 4.5:1; смысл не зависит только от цвета.
- Интерактивная цель не меньше 44×44px; hover никогда не является единственным способом получить действие или информацию.
- Icon-only control получает accessible name. Значимые изображения получают полезный alt; декоративные скрываются от assistive technology.
- Split/stagger text сохраняет цельное accessible name и читаемый статический вариант без JavaScript.
- Проверяй минимум 375, 768, 1024 и 1440px: отсутствие horizontal scroll, обрезанного текста и сломанных touch targets.
- Медиа ниже fold загружается лениво; размеры резервируются заранее; responsive formats выбираются по реальной необходимости.
- Не запускай бесконечную работу вне viewport или в скрытой вкладке. Любой canvas/WebGL обязан иметь DPR cap, pause, static fallback и полное освобождение ресурсов.

## Проверка перед передачей

Для изменения кода минимум:

1. `npm run lint`;
2. `npm run build` для production-кода, конфигурации, маршрутов и UI;
3. целевые тесты, если они существуют или были добавлены;
4. `git diff --check` и просмотр итогового diff.

Для визуального изменения дополнительно:

1. проверь desktop и mobile в реальном браузере;
2. проверь keyboard/focus, touch/coarse pointer и `prefers-reduced-motion`;
3. проверь loading/error/empty, если они достижимы;
4. сравни скриншот с design contract и убери минимум один лишний декоративный элемент;
5. проверь отсутствие placeholders, неподтверждённых claims, ложных logos/testimonials и недоступного split text.

Финальный ответ начинается с результата, затем перечисляет изменённые файлы, проверки и оставшиеся ограничения. Не описывай невыполненную проверку как выполненную.
